# Repository automation

The repository validates changes in CI and posts a rule-based review on pull requests. It does not automatically approve or merge contributions. The one automated merge is the [discovery ingest](#automated-discovery-ingest), which adds unreviewed scan records to their own queue and nothing else.

## Pull request review

`Automated PR review` uses the trusted base branch's reviewer. It retrieves selected JSON files as data from the exact PR commit and checks schema, duplicate IDs and URLs, source records, bilingual coverage, scope decisions, target labels, dates, and benchmark consistency. Source-index, localization, and scope changes are checked together against unchanged dependencies from the trusted base. Curated catalog changes and the Chinese names and requirements in `site/translations.zh-CN.json` are also checked together. Their value shapes are always checked. The reviewer reports a missing or unknown translation entry only for IDs the base catalogs do not contain, so a branch made before a newer record still passes; `scripts/validate.py` checks complete coverage on a full checkout. Automated source scans retain a separate status from curated resources. For curated records the PR adds or changes, evidence links that cannot show the reviewed revision (a GitHub wiki page without its revision, or a bare repository root) are listed under a separate advisory heading that names the record, field and URL; advisories do not change the check result, and records the PR does not touch are not listed.

The reviewer also checks added patch text, and the decoded string values of changed data JSON, for common credential patterns and personal filesystem paths. File names are checked against the private, generated and raw-output entries in `.gitignore`, common key and network-capture names, and licensed font files; these files are reported by path and never fetched. When GitHub omits a file's diff, the reviewer retrieves that file's text from the PR commit as size-bounded data for the same pattern checks. Files it cannot inspect, such as binary or oversized files, are listed for maintainer inspection before merging rather than reported as clean. Reports identify the file, and for data JSON the record and field where possible, without repeating suspected secrets. Pattern checks are a backstop, not a complete secret audit.

The job can write a review comment but does not check out or run the contributor's code, fetch contributor-provided external links, approve the PR, or merge it.

A pull request opened with the workflow token `GITHUB_TOKEN`, such as one opened by repository automation, starts no `pull_request_target` or `pull_request` run, so its required checks are started with `workflow_dispatch` instead. `Catalog checks` is dispatched on the PR branch, which runs its jobs on the branch commit exactly as a `pull_request` run of a same-repository branch would. `Automated PR review` is dispatched on the default branch with the PR number and the full head commit SHA as inputs, so both its workflow definition and its code come from that trusted branch; the PR head is still never checked out or executed. The dispatched job refuses to review unless it runs on the default branch and the PR is open, comes from a branch of this repository, targets the default branch and still has the named head commit. It posts the usual review comment, naming the default-branch commit whose code it ran, then records the result on the PR head both as a `review` commit status and as a completed `review` check run; it needs `statuses: write` and `checks: write` for that, which the `pull_request_target` job does not get. Branch protection counts the status: GitHub does not count the check runs of a dispatched workflow toward required checks (automation PR #2699 reported "2 of 2 required status checks are expected" while both check runs were green on its up-to-date head), but it does count a commit status set by GitHub Actions. For the same reason a dispatched `Catalog checks` run reports its aggregate result as a `validate` commit status on the commit it checked, from a separate `validate-status` job that runs only for `workflow_dispatch` and is the only job with `statuses: write`; pull-request and push runs keep a read-only token. A head that moves during the review gets no check. The up-to-date requirement still applies: a head that does not contain the current default branch cannot merge until it is updated and checked again. Code and workflow changes remain subject to maintainer review. Reviews are attached to a specific head commit. Every run revalidates the data; a repeated run updates the existing bot review and preserves the current check result. Report a weakness in this automation privately under the [security policy](../SECURITY.md), not in a public issue.

## Continuous integration

`Catalog checks` runs on pull requests, including those from forks, on pushes to `main`, and when dispatched on a branch. A newer push to a pull request cancels its superseded run; runs on `main` are never cancelled. Its checks run as parallel jobs. Each of the three `unit` shards, `unit (0)`, `unit (1)` and `unit (2)`, byte-compiles every script and test and runs its share of the tests that `python3 -m unittest discover -s tests -v` discovers. [tests/unit_shards.py](../tests/unit_shards.py) keeps each test class in one shard and checks that the shards are non-empty, pairwise disjoint and together equal the whole discovery, so together they run the whole suite once. `production` runs the production build command, `python3 scripts/build_production.py`. That build validates curated data and local Markdown links, checks generated README sections, the paper lists and the bilingual repository directory, checks JavaScript syntax, builds the collection website, runs the discovery and site validators, and runs the privacy check [privacy_guard.py](../scripts/privacy_guard.py) over the tracked files and the built site. That check, also a unit test, fails when a protected name, handle or personal link appears in a file, a file path or an archive member; it decodes UTF-16 text, reads zip and tar archives and gzip, bzip2 and xz streams within size bounds, fails on archive formats it cannot read, reads every other file as text (text drawn into images is out of its reach), stores only salted digests and reports files and lines without the matched text, printing a matching path component as `<redacted>`. No archive is exempt. `browser` installs the pinned `puppeteer-core` package from npm and runs the [browser smoke test](website.md#browser-smoke-test) in the runner's installed Chrome, keeping its screenshots as a workflow artifact. The `validate` job waits for these jobs and runs no check itself: it keeps the required check name and succeeds only when all three `unit` shards, `production` and `browser` succeeded, so a failed, skipped or cancelled job fails it. When `validate` fails, open the failed job for its log: a test or syntax failure is in a `unit` shard, a data, generated-file or site-validation failure in `production`, and a page-load failure in `browser`. Apart from that package installation, these jobs need no secrets or network access. The workflow has read-only repository permissions, and every job has a time limit.

The `main` branch requires the GitHub Actions `validate` and `review` checks, an up-to-date branch, and a pull request before merging. These rules also apply to administrators; force pushes and branch deletion are disabled. No human approval count is imposed, and the bot's review comment is not an approval. Use a feature branch and merge after the required checks pass.

`README lint` is a separate, non-required report. It runs the pinned awesome-lint 2.2.1 on README.md, and on docs/papers.md, which holds the paper lines moved out of README.md, for pull requests and pushes to `main` that change a README, a paper list, CONTRIBUTING.md, the README builder or the lint files, installing it from the [lockfile](../tests/awesome-lint/package-lock.json) without install scripts. Its job is not part of the `validate` aggregate and does not block merging. The job summary counts findings per rule for each file, and the `awesome-lint-report` artifact keeps every finding with its line for 14 days. On docs/papers.md, README-level rules such as `awesome-contributing` also report findings that do not apply to a list page. The workflow token is read-only; awesome-lint uses it only to read repository metadata. Spell-check findings that flag correct names, such as webpack, ReAct, Llama and Wasm, or ordinary words are recorded with a reason in the [allowlist](../tests/awesome-lint/allowlist.json) instead of being rewritten. Its `enforced_rules` names the rules whose unrecorded findings fail the job; none is enforced yet. To produce the same report locally:

```sh
npm ci --prefix tests/awesome-lint --ignore-scripts
node tests/awesome-lint/lint.mjs README.md
python3 scripts/awesome_lint_report.py .cache/awesome-lint/findings.json
node tests/awesome-lint/lint.mjs docs/papers.md .cache/awesome-lint/papers-findings.json
python3 scripts/awesome_lint_report.py .cache/awesome-lint/papers-findings.json
```

`PR hygiene` is a separate, non-required check of the maintainer's commit and review rules, run by [check_pr_hygiene.py](../scripts/check_pr_hygiene.py) from the base branch on every pull request event, including body edits. It fails when a commit message credits Claude, with a `Co-Authored-By: Claude` trailer or "Generated with Claude". In a pull request opened by reacher-z or a bot it also fails when a commit's author or committer is anyone other than reacher-z (`reacher-z@users.noreply.github.com` or the account's numbered noreply address) or a bot; GitHub as committer passes when the author does, and the merge commit that "Update branch" creates passes on its reacher-z address. A pull request opened by reacher-z needs a `Codex review` heading in its body with the review summary under it. Findings name a commit by its SHA and the failing field, never by the recorded name. The job reads the pull request through the API with a read-only token and never checks out its head.

The localization path was exercised in [PR #2](https://github.com/reacher-z/Awesome-REA/pull/2): valid data passed, an intentionally missing Chinese description failed both jobs, and restored data passed. Rerunning the reviewer updated the same head-specific bot review.

`Source links` runs weekly and on manual request. It checks the curated catalog, papers, benchmarks and the case ledger's reported and primary evidence links, and distinguishes confirmed missing links from rate limits and inconclusive network responses.

Every workflow action is pinned to a full commit SHA with its exact release version in a comment. Dependabot checks these actions weekly and groups available updates into one pull request, waiting seven days after a release before proposing it. Its pull requests run the same `validate` and `review` checks and, as workflow changes, need maintainer review.

## Triage source-link results

From the repository root, save a local report outside the checkout so it is not accidentally included in a contribution:

```sh
python3 scripts/check_links.py --json ../awesome-rea-link-report.json
```

The same checker runs in the `Source links` workflow. It saves the JSON report as a run artifact for 14 days and adds a counts summary, including when the checker reports confirmed dead links. Local runs save JSON only when `--json` is supplied. For slower or restricted connections, use `--workers 2 --timeout 30` and retry later rather than treating a timeout as removal.

Inspect `counts`, `complete`, and each result's `url`, `checked_url`, `references`, `status`, `reason`, and `attempts`. References identify the affected records and fields: `resource:<id>:<field>`, `paper:<id>:<field>`, `benchmark:<full_name>:<field>`, or `ledger:<entry id>:<field>` for a case-ledger entry's `reported_source_urls` or `primary_evidence_urls`. Curated resources are in `data/rea-resources.json` and `data/tool-resources.json`; papers and benchmarks are in `data/papers.json` and `data/benchmarks.json`; ledger entries are in `data/case-coverage.json`. One URL can have several references, so review all affected fields.

| Result | What it establishes | Next step |
| --- | --- | --- |
| `ok` | The final HTTP response was 2xx. | Check that the destination still describes the intended resource; an HTTP success alone does not verify its identity or claims. |
| `dead` | Two consecutive requests returned 404 or 410. | Check the original project's site, repository and release notices for a move, archival notice or removal before proposing a correction. |
| `recorded-missing` | Two consecutive requests returned 404 or 410, and every citing reference is a case-ledger entry whose `reason_en` already says this X post (by its @handle, or by its post ID for an `x.com/i/status/` link) or GitHub repository (by owner/name) was not found, in the sentence that names it, or a curated record whose `source_unavailable` field records the loss. | Nothing to fix; the ledger or the record already states the loss. If the source returns, update the entry's reason or remove the record's `source_unavailable`. |
| `reported-source-missing` | Two consecutive requests returned 404 or 410 for a link cited only in ledger `reported_source_urls`, the collection's own links, which the ledger lists without adopting as evidence. | Note the loss when the entry is reviewed; a reviewed entry should not rely on it as primary evidence. |
| `inconclusive` | Access restrictions, rate limits, network/server failures, a [refused redirect](#verify-a-moved-resource) or another response prevent a conclusion. | Leave the record in place. Inspect the attempts, retry after the restriction clears, or review the public primary source manually. Do not treat authentication walls, 403/429 responses or transient failures as confirmed removals. |

The command exits with status 1 when any link is confirmed dead. `recorded-missing`, `reported-source-missing` and inconclusive results alone still produce exit status 0: inspect `complete` and the counts before claiming all links passed. Do not add credentials to a report or commit raw reports to the repository.

### Verify a moved resource

The checker follows at most five redirects and records the final URL in each HTTP attempt. Before requesting a redirect target, it applies the same public HTTPS URL check as catalog validation: a redirect to plain HTTP, to a URL with embedded credentials, or to a local, reserved or non-public literal IP host is not followed. Such a refusal, and a sixth redirect, make the result `inconclusive`; the attempt keeps the last URL actually requested as `final_url`, the reason in `redirect_refused` and the refused target, without any credentials, in `refused_redirect_url`. The check is syntactic: hostnames are not resolved, so it does not detect a public name that resolves to a private address and does not protect against DNS rebinding. Compare the original `url`, the actual `checked_url`, and `attempts[*].final_url`. GitHub blob evidence is deliberately checked through `raw.githubusercontent.com` at the same revision; that conversion is not evidence of a project move. crates.io crate and version pages are checked through the crates.io API (`https://crates.io/api/v1/crates/<name>/<version>`), because crates.io answers page requests from non-browser clients with 404 even for published crates; the API returns 404 only for a crate or version that does not exist. Access restrictions such as HTTP 403 or 429 remain inconclusive. A login or access page returning HTTP 200 can still be reported as `ok`, so inspect the destination manually.

Before replacing a canonical URL, verify that the destination belongs to the same upstream resource using a maintainer announcement, a repository transfer/rename, or another primary-source statement linking the old and new locations. Check that the title, authors or owner, and relevant content agree. A redirect to a generic homepage, login page or unrelated mirror is insufficient. Preserve the stable catalog `id` and update only the affected URL/evidence fields and any review metadata supported by the new review; keep pinned evidence at a verified revision where appropriate.

### Record an unavailable source

When a curated record's own `url` returns 404 or 410 on two plain requests, and the project's site, owner account and release notices show no move, the record keeps its entry and gains `source_unavailable`, with the check time, outcome and HTTP status as the [catalog format guide](../data/README.md) defines. Entry pages then show the source status next to the review date, and this checker reports the record's links as `recorded-missing`. A renamed or transferred repository is a move, not a loss: follow [Verify a moved resource](#verify-a-moved-resource) instead.

### Submit a correction or retirement proposal

Use the [outdated-resource form](https://github.com/reacher-z/Awesome-REA/issues/new?template=broken-resource.yml) or a focused pull request naming the affected IDs, old URLs, observed statuses and check date. For a move, link the public primary evidence establishing the new canonical location. For retirement or replacement, explain the loss of the original resource and the reason for the proposed catalog decision publicly; do not silently substitute an unrelated mirror or reuse an existing ID for a different resource. If the evidence remains inconclusive, report that limitation and leave the entry unchanged pending review.

For a curated catalog correction, regenerate the derived indexes and run the contributor checks:

```sh
python3 scripts/build_readme.py
python3 scripts/build_repository_index.py
python3 scripts/validate.py
python3 scripts/build_site.py
node --check site/app.js
```

For paper changes, also follow the paper-specific validation and production-build steps in [the contribution guide](../CONTRIBUTING.md#suggest-a-research-paper). Review the diff for unrelated generated changes, then include the validation commands and results in the pull request. Keep source review distinct from runtime testing of the linked project.

## Plan source-review rechecks

`python3 scripts/review_age.py` lists curated resources and papers by the age of their last source review, so maintainers can plan rechecks. It runs offline from the repository root and reads `data/rea-resources.json`, `data/tool-resources.json` and `data/papers.json`; no workflow runs it.

```sh
python3 scripts/review_age.py --as-of 2027-04-01 --type paper --min-age-days 90
```

Age is the number of days from a record's `verified_at` date, converted to UTC, to `--as-of` (default: the current UTC date). Records are grouped into age bands and by record type, oldest first; `--bands` sets the day boundaries (default `30,90,180,365`). Each listed record gives its stable ID, catalog file, recorded review date, age and primary evidence link: `evidence_url` for a resource, the first `evidence_urls` entry for a paper. `--type` and `--min-age-days` narrow the list while the band counts still cover every record, and `--json` prints the full report. Records reviewed after the as-of date are counted separately.

The report is a planning queue. It leaves records and paper publication statuses as they are. The automated index's README `observed_at` times are summarized on a separate line and are never listed as source reviews. Updating a record after a recheck is a separate reviewed change; follow the [correction steps](#submit-a-correction-or-retirement-proposal).

## Merge a pull request by workflow

`Merge a pull request` merges one pull request with the workflow token `GITHUB_TOKEN` and the rebase method. A rebase keeps every commit's own author and records GitHub as the committer, whereas a squash or merge commit made by a person, and a rebase merge made by a person, put that account's name on `main`; merging through the workflow keeps personal account names out of the history. Start it from the default branch with the pull request number:

```sh
gh workflow run merge-pr.yml -R reacher-z/Awesome-REA -f pr=<number>
```

Before merging, [merge_pr.py](../scripts/merge_pr.py) refuses unless the pull request targets the default branch, is open and not a draft, is mergeable (it waits up to two minutes for GitHub to compute that), has a head that contains the default branch's current commit, and has a successful `validate` and `review` check on that head: the newest commit status of that name, which dispatched automation checks report, or otherwise the newest GitHub Actions check run of that name. It also waits, up to two minutes, until GitHub reports the pull request mergeable under branch protection. The merge step then rebase-merges with `--match-head-commit`, so only the commit that was checked can land, asking twice more if GitHub refuses while still recomputing; branch protection still applies to the merge. A same-repository branch is then deleted by a push with a lease on the merged head, so a branch that received new commits after the merge is kept. Runs for one pull request are serialized; the job has `contents: write` and `pull-requests: write` to merge, read access to checks and statuses, `actions: write` to start the [IndexNow notification](#indexnow-notification) for the merged commit (a failed start only warns), and a 10-minute limit. Pushes made with the workflow token start no `push` workflows, so `Catalog checks` does not rerun on `main` for a merge whose head it already checked; Cloudflare Pages still deploys the new commit.

## Website delivery

See [website building and publishing](website.md) for the static build and hosting setup. Production uses the public source repository. Credentials, private configuration, raw analysis output, and deployment bundles are excluded from the public repository.

The production build command runs `scripts/build_production.py`. It stops deployment if catalog validation or JavaScript syntax validation fails. Cloudflare's existing Git connection builds each change to `main` and creates PR previews; no deployment API token is stored in this repository.

### IndexNow notification

`Notify IndexNow` ([indexnow.yml](../.github/workflows/indexnow.yml)) tells the [IndexNow](https://www.indexnow.org/documentation) engines (Bing, Yandex, Seznam, Naver, Yep and the other participants) which canonical pages a production deployment added or changed. Google does not take part; it reads the sitemap index and its `lastmod` dates. Cloudflare Pages reports a deployment only as its `Cloudflare Pages` check run, and a `check_run` event never starts a workflow for a commit that GitHub Actions pushed, which is how pull requests and discovery batches now reach `main`. So `Merge a pull request` and the discovery ingest start the workflow with the merged commit, and a schedule every three hours (minute 41) catches deployments made any other way.

1. **Build.** The run checks out that commit, refuses one that is not on the default branch, and builds it with `build_site.py` and the asset URL of the Cloudflare Pages build command, which reproduces the deployed files byte for byte.
2. **Wait.** [indexnow_automation.py](../scripts/indexnow_automation.py) waits, at most 25 minutes, until awesomerea.org serves that build: its public `build-manifest.json` must equal the local one. The commit's Cloudflare Pages check run tells a deployment still in progress from one that failed (the run fails) or one a newer commit replaced (the run stops without notifying; the newer commit's run covers both). A completed deployment that still serves other bytes for three minutes fails the run, because verification needs a reproducible build.
3. **Baseline.** It downloads the `indexnow-receipt` artifact of the newest earlier successful run of this workflow on the default branch: that run's `receipt.json` and the `build-manifest.json` it notified, which must match the receipt's SHA-256. Without one, every sitemap URL is notified.
4. **Notify.** `submit_indexnow.py --submit --automatic` compares the two manifests and sends one POST with the added and changed canonical pages, after verifying the ownership file, the sitemap files, the manifest and every canonical page of the deployment. Changes to data files or assets alone notify nothing. It never retries a POST; a failed one fails the run, and the next run diffs from the same baseline, so nothing is lost.
5. **Receipt.** The new receipt and manifest are kept as the `indexnow-receipt` artifact for 90 days, as the next run's baseline.

Runs share one concurrency group and queue rather than overlap. The job reads the repository, checks and Actions artifacts only; the IndexNow key is the public ownership file `site/indexnow.txt`, so no secret is involved. HTTP 200 or 202 confirms receipt, not indexing.

## Scheduled README discovery

For complementary GitHub Discussion, public-directory and X-excerpt link snapshots, see [public artifact lead discovery](public-artifact-discovery.md). It runs separately every eight hours and retains an unreviewed URL queue; it does not change the README scanner, its goal, or the curated catalog.

`Scheduled README discovery` runs **every eight hours at minute 7 UTC** (`7 */8 * * *`: 00:07, 08:07, 16:07) and can be started manually from the default branch. [GitHub can delay scheduled jobs](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule); these are requested start times. A run that is still going when the next one is due delays it rather than overlapping, because runs share one concurrency group; recent runs take 17 to 38 minutes from start to finish.

The scheduled collection target is **160,000 distinct README captures with an explicit Git blob hash match** (`readme_git_sha_matches_content: true`). Each run seeks at most **2,000 new verified captures**, clamped to the qualified count remaining after reconciling the published index with the last checkpoint. Legacy records without a comparison flag and known mismatches remain in the raw evidence, but consume none of this goal. A raw total of 160,000 with only 159,950 qualified captures therefore still plans 50. The child receives a raw-record target of retained records plus the planned verified additions; the parent rejects any new success without explicit verified integrity. At the qualified goal, no discovery or README requests are made. Search results, metadata lookups, failed reads and duplicate IDs do not count toward the goal. The target does not assert that this many relevant repositories exist or that the collection is complete.

The initial REST scheduler was verified with 300 new reads in its first run. The next version uses the separately verified GraphQL transport with **16 repositories per batch**, at most **360 search requests** and **200 legacy metadata lookups** per run. The candidate surplus is 10% of the planned verified additions, bounded to 50–200, so unavailable or invalid README files need not end a run just short of its target. The larger discovery budget retains the same time, GraphQL request/cost, quota-reserve and REST-fallback limits; reaching 2,000 is not guaranteed. It keeps the existing public/non-fork/non-archived scope gates and adds explicitly approved Website/Game/App queries: screenshot-to-code, website clones and reconstruction, pixel-perfect clones, game recreation/reimplementation, UI reconstruction and app clones, plus README and description phrases for reimplementations, decompilations, clones and ports. New roots append to the saved frontier without resetting previous partitions or cursors. The frontier partitions bounded UTC creation intervals instead of repeatedly taking only the first 1,000 results of a broad query. Search-hit populations overlap and do not establish how many successful or relevant resources are available; broader discoveries require separate scope review and never automatic curation.

The [public verification run](https://github.com/reacher-z/Awesome-REA/actions/runs/39315608648), limited to 120 search requests, queued 956 candidates: 948 first discovered by search and 8 from metadata seeding. It yielded 935 verified reads in about 12 minutes at 180 reported GraphQL points. The 360-request ceiling tests whether additional bounded discovery can fill the planned batch. It continues the same saved cursors and scope, and the scan deadline can still produce a partial checkpoint; a larger request budget is not a promise of higher measured throughput.

Runs are serialized. The 30-minute job gives restoration and scanning a combined **24-minute budget**, reserving time for validation and artifact upload. Searching stops at minute 12 of that budget and reading takes the rest, so a run with few new search results still reads the candidates it has; the frontier resumes the remaining searches on the next run. Three scheduled runs a day use the 24-minute scan budget; each still seeks up to 2,000 verified reads, but its time budget, quota and available candidates usually end it sooner. GraphQL pauses on observed rate limits and transient backpressure; it does not evade those signals through REST. A failed GraphQL request costs its batch of 16, which goes back in the queue for a later run; reading continues after 5 seconds, up to 5 times a run. The scheduled wrapper also stops new batches after 800 reported GraphQL cost points or requests, preserves a 100-point remaining reserve, and offers at most 200 REST fallbacks, subject to observed remaining quota. Actual outcomes and available query-cost metrics are retained. Missing cost information is not treated as a measured zero-cost query.

A bounded invocation succeeds when it reaches its planned increment, or when an expected shortfall (scanner exit 1) or controlled time limit (124) saves at least one new verified capture in a fully validated checkpoint pair. A partial result keeps its original scanner exit, `partial`/`time-budget` outcome, original snapshot status and actual target flags; it is never relabeled complete or made publishable. No-progress shortfalls, unexpected child failures, damaged evidence and validation failures still fail the job. The CLI's exit semantics, quotas and publication checks are unchanged.

[GitHub's repository token receives 1,000 REST requests/hour](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api) and [1,000 GraphQL points/hour](https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api), shared with other uses of that repository token. Batch size and planned increment are not throughput guarantees; rate limits, failures, search boundaries or the time budget can yield a partial run.

The scan job has only `contents: read` and `actions: read`. Its ephemeral `GITHUB_TOKEN` is supplied only to the scanner step. It does not execute upstream code, write source files, create PRs or post comments. README text is read, verified, summarized into document features and hashes, and discarded; it is not included in artifacts. The separate `ingest` job, described [below](#automated-discovery-ingest), is the only part of the workflow that can write, and it never promotes discoveries into the curated catalog.

### Paired checkpoints

The version-2 `readme-scan-checkpoint-<run attempt>` artifact contains exactly **`checkpoint.json`, `frontier.json` and `receipt.json`**. The receipt binds both data files' SHA-256 hashes and byte sizes to the same workflow run, attempt and source commit. The next run restores a completed run of this same default-branch workflow and repository, including a validated partial checkpoint from a failed or timed-out run. Earlier attempts of a manual rerun can be resumed. A version-1 two-file artifact can seed the scan state and create a new frontier; a damaged version-2 pair is never silently downgraded.

The scanner saves actual capture evidence before acknowledging its numeric IDs in the frontier. After a timeout, the parent waits for the child to stop, validates both files, and repairs only the safe scan-saved/frontier-not-yet-acknowledged case. An acknowledged ID absent from the paired scan evidence stops restoration. The receipt is written last, and upload is enabled only after the complete pair validates. Working files, `.tmp` files, raw responses, logs and environment dumps are never uploaded.

When the published index advances, reconciliation preserves checkpoint-only captures and the pending-ID union. Success takes precedence over a failed attempt for the same ID; published successful versions take precedence over older versions. Input hashes, original counters and superseded-record hashes preserve provenance. Different numeric IDs claiming the same repository name stop for review with both validated inputs retained. Counts are recomputed from unique identities, not added across snapshots.

A checkpoint marked `in-progress` is resumable but remains rejected by the normal publication validator. Before any authentication, resuming applies the publication validator's hash, URL, repository-visibility and discovery-provenance checks to the retained evidence; completion, the population guard and the remaining fields of a finished record stay publication-only. The scheduler requests explicit incomplete-checkpoint validation without changing that status. Review relevance, source scope, attribution and bilingual descriptions separately before a normal publication PR.

### Bounds and retention

Evidence-file capacity does not relax remote-response limits. Ordinary API JSON responses remain bounded to **12 MiB**; the scan member is bounded to **512 MiB**, the frontier to **256 MiB**, and the receipt to **8 MiB**. The compressed archive is bounded to **512 MiB**, and the sum of uncompressed members to **776 MiB**. Archive downloads and member hashes are streamed; JSON is parsed once per validation, retained records are not deep-copied during reconciliation, and the parent releases full input objects before the child starts. These are enforced bounds, not a claim that a full 160k end-to-end run has been measured.

Version-2 artifacts have **7-day retention** to avoid retaining 90 days of growing full snapshots. At the target, an unchanged paired checkpoint with more than 48 hours left is reused without re-encoding or uploading another copy; a near-expiry checkpoint is renewed to maintain continuity. Canonical changes and version-1 migration can also require a fresh pair. No other artifacts are automatically deleted and repository permissions are not widened. Keep a separately verified durable milestone backup before long pauses: after retention expires, the job stops for recovery rather than silently restarting from a smaller snapshot.

The run summary reports qualified captures, raw retained captures, legacy integrity-unknown captures, known mismatches and failed attempts separately. New version-2 receipts add `goal_basis: explicit-git-blob-sha-match`, `retained_integrity_counts`, `integrity_counts` and `new_qualified_successful_scans`. Each integrity-count object partitions the raw capture count into `qualified`, `legacy_unknown` and `mismatched`; all four receipt fields must appear together. `global_target_reached` follows qualified captures, while `run_target_reached` follows the planned verified increment. Older receipts remain readable, and their global-goal flags are recomputed from retained records before scheduling. Bootstrap-only imports preserve exact raw evidence with zero new verified reads. Artifacts remain a discovery queue, separate from the reviewed public source index and search-engine indexing.

For a separate private worker that starts from reviewed local evidence, see [private scan worker bootstrap](private-scan-worker.md). This first-import path uses a pinned public scanner, a bounded gzip seed and private artifacts; it does not activate a second schedule or change the public catalog.

### Scan status badge

The README's scan badge is a [shields.io endpoint badge](https://shields.io/badges/endpoint-badge) that reads `scan-status.json` from the `status` branch. `Scan status badge` ([scan_status_badge.py](../scripts/scan_status_badge.py)) rewrites that file every hour and after every README discovery scan: it shows when the last successful scan of `main` finished, a run of the workflow that concluded `success` (a run with nothing to ingest skips its ingest job and still counts), and turns amber once that is more than six hours ago. The branch holds only this file; the first run creates it, and later runs commit only when the badge changes, as the workflow bot.

## Automated discovery ingest

After a scan saves its checkpoint, the workflow's `ingest` job adds a bounded batch of the new verified captures to the [unreviewed discovery queue](../data/discoveries/README.md) and publishes it without a person, as the repository owner asked. The automation may merge only this kind of change: one new `data/discoveries/run-<run id>-<attempt>.json` file of exact scan records, all still `automated-readme-scan` and `unreviewed`. Curated records, the source index, public supplements, translations, scope decisions and generated files are never touched, and nothing is promoted to `source-reviewed`.

1. **Restore.** The job downloads this run's checkpoint artifact and validates it with the scanner's own restore checks: archive digest, members, receipt binding to the run, attempt, workflow and commit, counts and integrity counts.
2. **Prepare.** On the default branch's current commit, and with that commit's code, it selects up to 300 captures under the [queue's selection rules](../data/discoveries/README.md#selection-rules), newest first, and writes them unchanged with their provenance. A run with nothing new adds nothing and opens no pull request; there are no empty commits.
3. **Validate.** It runs `python3 scripts/validate.py`, `python3 scripts/discoveries.py` and any `tests/test_privacy*.py` regression test on that tree before committing.
4. **Pull request.** It commits only the batch file onto the default branch's current commit, through the Git data API, as `Ingest <N> unreviewed discovery records from scan run <run id>`, force-updates the `automation/discovery-ingest` branch and opens or updates one pull request from it. The repository setting *Allow GitHub Actions to create and approve pull requests* must be on for the workflow token to open it; no personal token is stored.
5. **Required checks.** A pull request opened with `GITHUB_TOKEN` starts no `pull_request` or `pull_request_target` run, so the job [dispatches both required checks](#pull-request-review): `Catalog checks` on the PR branch, which reports `validate` on the head commit, and `Automated PR review` on the default branch, whose trusted code reviews the batch as data, including that it only adds a batch and that every record is new to the base branch's layers, and reports `review` on the head commit. Both report their results as commit statuses, which branch protection counts, and the job waits for those statuses. Branch protection is unchanged: a pull request, both checks from GitHub Actions and an up-to-date branch are still required, administrators included.
6. **Merge.** When both checks pass on the head commit, the job waits, at most four minutes, until GitHub has recomputed the pull request as mergeable, then rebase-merges that exact commit, so `main` gets the one commit with its fixed message and the workflow bot as author; a merge refused while the branch is still current is asked again up to three times. If the default branch moved first, it rebuilds the batch on the new commit, force-pushes, dispatches the checks again and retries, up to three attempts within the job's 90 minutes; a failed check stops it. After the merge it deletes the branch and starts the [IndexNow notification](#indexnow-notification) for the merged commit. Pushes made with `GITHUB_TOKEN` start no `push` workflows, so `Catalog checks` does not rerun on `main` for an ingest merge whose head it already checked; Cloudflare Pages builds production from the new `main` commit through its own Git integration, independent of Actions.

A merged batch reaches awesomerea.org after the scan, ingest checks and Cloudflare Pages build. Scans are requested every eight hours; a run uses about 25 minutes of scanning and 15–35 minutes of ingest and checks. The website shows the newest records at [/discoveries/](https://awesomerea.org/discoveries/) and exports them, labelled unreviewed, in `/discoveries.json`, `/discoveries/feed.xml` and `llms.txt`; `/discoveries/status.json` gives the last successful ingest time.

**Failure tracking.** The workflow's `report` job, and the same job in `Public artifact lead discovery`, keep one tracking issue per workflow. A failed or cancelled run opens the issue, or reopens the most recent one, with the run link; further failures only edit its body (failure count, first and latest failure, job results, last successful ingest), so they do not notify watchers again. The next fully successful run comments and closes it. An ingest failure leaves its pull request open for inspection; the next run's pull request replaces it on the same branch.

**Budget.** A batch holds at most 300 records, and the queue at most 25,000 records and 64 MiB; at either limit the ingest fails and its tracking issue explains why. See [growth budget](../data/discoveries/README.md#growth-budget).

## Followed-source lead discovery

`Followed-source lead discovery` ([discovery-leads.yml](../.github/workflows/discovery-leads.yml)) runs **every eight hours at minute 7 UTC** (`7 */8 * * *`), the same requested start as the README scan, and can be started manually from the default branch. It follows the public sources registered in [data/discovery-sources.json](../data/discovery-sources.json): other reverse-engineering list READMEs, GitHub topics, the Binary Ninja, radare2-pm and SubmitGame registries, the bibliographies of curated surveys, an arXiv query and Hugging Face searches. What they list becomes unreviewed leads in the [discovery queue](../data/discoveries/README.md#followed-source-leads); nothing is curated, translated or marked `source-reviewed`.

1. **Collect.** The `collect` job has only `contents: read`. It reads each due source at its current revision (GitHub files at the default branch's current commit, verified against their Git blob IDs), parses its listings, applies the registered section, keyword and exclusion rules, resolves every GitHub repository to its numeric ID and uploads the in-scope candidates as a three-day artifact. Sources marked `every_hours` (GitHub topics, surveys, SubmitGame, Hugging Face) use an eight-hour slot: 12-hour sources run about every 16 hours and 24-hour sources once a day, spread by ID. A manual run with `all_sources` follows all of them. A source that fails is recorded as `error` with its reason and the run continues; a failed repository lookup skips its source, leaving other sources available for ingest.
2. **Ingest.** The `ingest` job downloads that artifact, never upstream text, and repeats the README ingest's path on its own branch, `automation/discovery-leads`: it selects up to 2,000 leads that are new to every repository layer with the default branch's current code, runs `python3 scripts/validate.py`, `python3 scripts/discovery_leads.py` and any privacy test, commits only the new `data/discoveries/leads/<YYYY-MM>/leads-<run id>-<attempt>.json` through the Git data API, opens or updates its pull request, dispatches the required `validate` and `review` checks and rebase-merges when both pass, so `main` keeps the workflow's own commit and author; squash and merge commits would carry the merging account's display name. If the default branch moves first it rebuilds the batch and retries, as described [above](#automated-discovery-ingest). A run with nothing new opens no pull request, and neither does one whose registry changed after collection: candidates gathered under other scope rules wait for the next run.
3. **Review.** The trusted `review` check validates an added lead batch with the default branch's code: schema, pinned listing evidence, fingerprints, run provenance and identities new to every base layer, plus the budget. It accepts lead batches only from this workflow's pull request, which changes nothing else; a registry change is checked against the base's registry rules.

**Timing.** The two ingests share one requested start because that keeps them apart. Workflows requested for the same minute start within about two minutes of each other. A collection takes 2 to 3 minutes and an ingest at most about 5, while the README scan reads for at least 12 minutes before its ingest. A later offset would not help: the README ingest starts anywhere from about 25 to 55 minutes after the scheduled start, depending on GitHub's delay. If they do overlap, the later ingest rebuilds its batch on the new commit and retries, as described [above](#automated-discovery-ingest).

**Bounds.** The collector makes at most 600 requests in 18 minutes inside a 25-minute job. Requests go only to allowlisted routes: GitHub GraphQL and Git blobs (with the workflow token, which no other host receives), arXiv HTML pages and its export API, the Semantic Scholar references endpoint and the Hugging Face model and dataset search. Redirects are followed only within the same host and route allowlist; responses are capped at 8 MiB (16 MiB for GraphQL). It waits 15 seconds between arxiv.org requests, as its robots.txt asks, 3 seconds between arXiv API calls and stops a host on a rate-limit response; GitHub calls stop when fewer than 200 requests remain. A batch holds at most 2,000 leads and 4 MiB; the queue at most 30,000 leads and 48 MiB, after which the ingest fails and its tracking issue explains why. Failures update one tracking issue, as for the README scan.
